1. Custom AI System Design（独自AIシステム設計・構築）
■ 概要
企業固有の課題（例：在庫最適化、製造ライン不良検知、与信スコアリングなど）を解決するために、
要件定義 → データ収集 → モデル選定・設計 → プロトタイプ実装 → 本番環境リリース までを一気通貫で行うサービスです。

単なる「PoC（概念実証）」にとどまらず、実際に動く高精度モデルとその周辺インフラ（APIサーバー、ダッシュボード、バッチ処理など）までを設計・開発します。

■ 想定アウトプット例
ダッシュボード画面のスクリーンショット

例：

「在庫最適化ダッシュボード」（予測結果グラフ + リアルタイム更新）

「不良検知アラート画面」（製品画像のサムネイル × アラートマーク + 検知確度）

Figma で作成した高解像度モックアップを、“あたかも本番稼働中の画面”に見せる。

システムアーキテクチャ図（SVG or PNG）

「データ取得 → 前処理 → モデル推論 → 戻り値配信 → ダッシュボード更新」の流れを一枚で示した図。

AWS ／ GCP ／ Azure など実際に使うクラウドサービスをアイコン付きで配置し、技術選定の根拠がひと目でわかるようにする。

短尺デモ動画（MP4 or WebM）

30～45 秒程度で、下記のような流れを画面収録＋テロップで見せる：

「要件ヒアリング → モデル設計 → プロトタイプ開発」の概要（音声ナレーション or キャプション）

Figmaモックで描いたダッシュボードを操作し、リアルタイムで推論結果が反映される様子

バッチワークフローでモデルを定期再トレーニングし、結果が自動更新されるシーン

「Client: Example Corp.」「Outcome: 予測精度 92% → 97%」「ROI 1.3 倍」などの成果スライド

2. AI Integration into Legacy Systems（既存システムへのAI組み込み）
■ 概要
既に運用中の社内システム（ERP, CRM, 在庫管理, 顧客管理など）に対して、後付けでAIモデルを組み込むサービスです。

例えば、

既存の受注システムに「需要予測モデル」を紐づけて自動発注をトリガー

既存の製造管理システムに「不良品検知AI」を連携し、ライン停止・再稼働制御を自動化

既存のCRM に「顧客解約予測モデル (Churn Prediction)」を組み込み、営業部門にSlack通知する

複数のレガシーAPI (SOAP または REST) / DB（オンプレ/PostgreSQL/Oracle）を橋渡ししながら、AIを後付けで“継ぎ足す”アーキテクチャを設計・実装します。

■ 想定アウトプット例
レガシー連携フロー図（SVG）

左側に「既存 ERP (オンプレ)」「既存 CRM（クラウド）」を配置し、

右側に「AI推論マイクロサービス (FastAPI など)」「メッセージングキュー (Kafka / RabbitMQ)」「Slack 通知」などを配置したシステム図。

矢印で「データ取得 (API or DB 接続) → モデル推論 → 戻り値 REST API 返却 → 既存画面に反映 or 通知」という流れを示す。

UIモックアップのBefore/After スクリーンショット

例：

Before: 既存の販売管理画面（手入力での発注数表示のみ）

After: 新たに追加された「AI推奨発注数」フィールド + 「推奨理由 (グラフ)」ポップアップ

Figma で「既存システムっぽい画面」を再現し、左が旧画面、右がAI機能組み込み後画面という形式で並べる。

n8n または Zapier を使った自動化ワークフロー動画

例：

「定期バッチで Oracle DB から売上データを取得」

取得データを AI モデルに送信し、予測結果を受け取る（Python スクリプト or FastAPI 呼び出し）

予測結果を既存 CRM の “Churn Risk” フィールドに自動登録し、

人事システムに対してSlack通知を行う流れ

これを 30 秒ほどで収録し、「AI 組み込みでレガシーを進化させる方法」を直感的に見せる。

3. AI-Driven Automated Workflows（AI駆動型業務自動化／RPA連携）
■ 概要
単純ルールだけではなく、AIによる推論結果に応じて分岐・判断を行う自動化ワークフローを作成し、
RPA やノーコードツール（n8n / Zapier / Make）を使って「人手が介在していた作業」を一気に半自動化・全自動化します。

代表的なユースケース例：

Web 上のニュース記事をクロール → NLP モデルでトピック分類 → カテゴリごとに Slack 通知 or Google Sheets 連携

顧客からの問い合わせメールを Gmail API で取得 → AI チャットボットに要約＋返信文生成 → 自動ドラフト送信 or 担当者アラート

IoT センサーのアラートデータを取得 → 画像分類モデルで「異常有無」を判定 → しきい値超過で PagerDuty 呼び出し＋メール

■ 想定アウトプット例
n8n ワークフローダイアグラム（SVG or PNG）

ノード間を結ぶ矢印で「データ取得 → AI推論 → フィルタリング → メール送信 / Slack 通知」を可視化。

各ノードにアイコン＋“What it does” を英語で記載。

ワークフロー実行のデモ動画（MP4）

30 秒程度で、

「トリガー（Webhook or CRON）」が動いている状態をキャプチャ

AI ノードを実行し、モデルが動く様子を録画（モデルの推論確率などが見える）

最終的に「Slack に自動通知が飛ぶ」様子 or 「Google Sheets が更新される」様子を見せる。

Before/After 図解

Before: 手動でニュースサイトをチェックし、手作業でExcelにまとめ、メール送信していたフロー

After: n8n + AI で「完全自動化 → Slack 通知 or Google Sheets アップデート」のフローに進化

矢印とテキストのみで構成したシンプルな一枚図を用意し、サービス概要ページにも掲載。

4. Predictive Analytics & Forecasting（予測分析・需要予測ソリューション）
■ 概要
過去のデータ (売上・生産・顧客行動・在庫) をもとに、時系列モデル（LSTM / Prophet / ARIMA / XGBoost など） を構築し、
将来の数値（売上予測・設備故障予知・人流予測など）を提示することで、企業の意思決定を支援するサービスです。

たとえば、

小売店舗の週次販売量予測 → 最適発注数の自動算出

製造機械のセンサーデータを使った故障予知 → メンテナンスのタイミング通知

Web サイトのユーザー行動データをもとにしたアクセス予測 → 広告配分最適化

■ 想定アウトプット例
予測モデルアーキテクチャ図（SVG/PNG）

「データ収集 (CSV/DB) → 前処理 (Pandas) → 特徴量エンジニアリング → モデル学習 → 推論 → 可視化 (BI Dashboard)」

使う技術スタック（Python, TensorFlow, Prophet, AWS SageMaker, Tableau など）をアイコン付きで示す。

BI ダッシュボードスクリーンショット or モックアップ

例：Tableau や Power BI 風の折れ線グラフで「過去実績 vs 予測値」を比較表示した画面。

予測結果をマウスオーバーすると「誤差」や「信頼区間」が表示されるモックアップを 1 枚用意。

短尺予測デモ動画（MP4）

30～45 秒程度で、

過去データを読み込む

モデルを実行し、その推論結果がグラフに自動レンダリングされる

BIダッシュボードで「フィルタ (地域/月)」を切り替えると予測グラフが動く

キャプションや吹き出しで「Forecasting accuracy: 95%」「MSE: 0.02」などの数値を動的に追記。

5. MLOps & Model Deployment (AIインフラ構築・MLOps)
■ 概要
モデルを「作って終わり」ではなく、本番環境で安全かつスケーラブルに運用する仕組み（MLOps パイプライン）を構築するサービスです。

典型的な流れ：

コード管理 (GitHub/GitLab でモデル & 前処理スクリプトを管理)

CI/CD (GitHub Actions / GitLab CI でテスト → Docker Image ビルド → コンテナレジストリへプッシュ)

コンテナ化 (Docker + Kubernetes / EKS / GKE / AKS)

オーケストレーション (Argo CD / Helm / Terraform などでインフラをコード化)

モニタリング & ロギング (Prometheus / Grafana / ELK Stack でパフォーマンス監視/ログ分析)

モデル再学習 (定期バッチ or イベントドリブンで、最新データを使って再学習 → ベータ検証 → 本番ロールアウト)

■ 想定アウトプット例
MLOps ストリームライン図（SVG）

上流 (Data Ingestion) → モデル学習 → テスト → イメージビルド → 本番デプロイ → モニタリング → 再学習 の一連のフローを一枚の図に。

「GitHub → GitHub Actions → Docker Hub → EKS → Argo CD → Prometheus → Grafana → Slack 通知」といった技術をアイコンで示すと説得力が増す。

デプロイパイプラインの画面キャプチャ / モックアップ

GitHub Actions のワークフロー画面で「Passed ✅」の緑色バッジが付いている様子。

Kubernetes Dashboard 上で「Pod が稼働中」かつ「ReplicaSet が 3 インスタンスにスケール」している画面イメージ。

Grafana のダッシュボードで、API レイテンシ / CPU 使用率 / メモリ使用率がリアルタイムに可視化されているグラフ。

短尺デモ動画（MP4）

30 秒ほどで、

GitHub へ新しいコードを Push →

GitHub Actions が自動でテスト → Docker Image ビルド →

イメージが EKS にデプロイされる（kubectl logs / kubectl get pods 画面） →

Grafana でトラフィックが増えた瞬間に Pod がオートスケールする様子

テロップや吹き出しで「CI/CD → 自動デプロイ → オートスケーリング → モニタリング」の流れを説明。

どれも「企業が実際に投資したくなる分かりやすいテーマ」になっており、ビジネスのフェーズや目的に応じて訴求しやすい。

各柱ごとにサムネイル・スクリーンショット・デモ動画を用意

/public/images/usecases/uc-***-thumbnail.png および /public/images/usecases/uc-***-screenshot*.png：最低各柱につきサムネイル 1 枚 ＋ スクリーンショット 2 枚を用意。

/public/demo/uc-***-demo.mp4：各柱ごとに 30～45 秒程度の短尺デモ動画を設置し、ボタンをクリックすると再生できるようにする。

データ構造上の統一性

id: “英小文字＋ハイフン区切り” で統一。

title: ページ表示用のキャッチーな名前。

thumbnail: 一覧ページで見せる、各柱のイメージがひと目で分かるデザイン。

shortDescription: 一覧ページのカードで表示される 1～2 行の簡単サマリー。

detailData.description: HTML タグを交えた詳細説明。見やすさ重視で <p><strong>... を適度に使う。

screenshots: 詳細ページのギャラリーとして表示する画像パスの配列。

videoDemo: /public/demo/ に置いた動画ファイルの相対パス。空文字列にすると「動画なし」と判断し自動で表示をスキップ。

techStack と outcome: 箇条書きで表示しやすい配列形式に統一。

３．実装後のデザイン確認ポイント
ユースケースが５件であることを直感的に分かるように見せる

ページを開いたときにカードの列数や余白によって「５件だけ並んでいる」構成が適度にスッキリ見えるか。

３列レイアウトであれば、右下に余白（空カード枠なし）が自然に見えるよう、justify-center や mx-auto の調整を行う。

詳細ページ（[id].jsx）のビジュアルチェック

すべての見出し、段落、箇条書き、画像、動画プレーヤーが 背景が黒に対して白文字・グレー文字・黄色アクセント で視認性が高いか。

「Custom AI System Design」などのタイトルだけでなく、成果 (outcome) の箇条書きが読みやすい行間・フォントサイズになっているか確認。

各ユースケースの「柱であること」を強調

各詳細ページの冒頭で <p><strong>サービスの柱：</strong>Custom AI System Design</p> のように、“このページが何を示しているか”が 1～2 行で理解できること。

目次的に <h2>Video Demo</h2> / <h2>Screenshots</h2> / <h2>Tech Stack Used</h2> / <h2>Key Outcomes</h2> の見出しレベルが揃っているか確認。

レスポンシブ対応

ブラウザをモバイル（スマホ）表示にして、カードが 1 列に縦に並ぶか、テキストが潰れないか、ボタンがタップしやすいサイズかをチェック。

タブレット表示（幅 768〜1024px）では 2 列レイアウトが自然か、ボタンや動画のサイズ感が適切かを確認。

デスクトップでは 3 列 → 5 件なので「最後の 2 枚は左右中央寄せで見栄えが良いか」を見て、必要なら justify-center や mx-auto を微調整してギャップを埋める。

アクセシビリティチェック

コントラスト比：テキスト（白 #FFFFFF, グレー #CCCCCC または #AAAAAA など）と背景（#0F0F0F / #1A1A1A）のコントラストが WCAG AA をクリアしているか。

alt 属性：すべての <Image> に alt="..." が適切に設定されているか確認。

キーボード操作：Tab キーでカード → リンク → ボタン → 動画 → 戻るリンク と論理的にフォーカスが移動するかをテスト。

パフォーマンス & SEO チェック

画像最適化：Figma 等からエクスポートした PNG があまりにも重くないか。できれば 200～400KB 以下に抑えるか、JPEG/WEBP に変換して軽量化する。

動画ファイルサイズ：MP4 は 30～50MB 以内に収める。特にモバイルでは画質を落としても 720p で十分。

Lighthouse で Performance・Accessibility・Best Practices・SEO を測定し、

Performance: mobile: 80 点以上／desktop: 90 点以上を目指す

Accessibility: 90 点以上を目指す

SEO: 80 点以上を目指す

構造化データ（Schema.org）：詳細ページに <script type="application/ld+json"> を挿入して、個別ユースケースを Schema.org の WebPage としてマークアップしておくと、検索結果のリッチスニペットで有利になります。
